# 慢查询 demo:索引 / 预聚合 / 游标分页(零依赖)

配套文章:《查询优化:慢查询怎么治 —— 索引 + 预聚合》

这个 demo **不用装 MySQL** —— 用内存数组模拟一张几万行的"订单明细表",
聚焦把慢查询的根因和提速手段**用「扫描行数 + 耗时」直观看出来**。

慢查询的本质,往往就是一句话:**扫的行太多**。下面三个场景,各演示一种"少扫行"的办法。

## 怎么跑

```bash
node demo.js
# 或
npm start
```

跑完即退出,不常驻。

## 演示了什么

| 场景 | 慢在哪 | 提速手段 | 看什么 |
|---|---|---|---|
| 一 · 点查 | 按 userId 全表扫 O(n) | 建索引(userId→订单),按 key 直达 | 扫描行数 50000 → 50 |
| 二 · 聚合 | 每次刷新都实时 `GROUP BY` 全表 | 预聚合成"每天汇总表",查一行现成的 | 扫描行数 50000 → 1 |
| 三 · 深分页 | `offset` 要逐行读出再丢 | 游标(书签法),按上次最大 id 续上 | 扫描行数 40020 → 20 |

注意场景一、二里都有一行"(一次性)建索引 / 预聚合耗时":索引和汇总表是**一次性成本**,
建好之后每次查询都受益。慢查询治理的取舍,就在这里 —— 用一份额外维护的结构,换每次查询少扫很多行。

## 文件

- `lib.js` —— 订单明细表(内存数组)+ 全表扫 / 索引 / 实时聚合 / 预聚合 / offset / 游标分页(带中文注释)
- `demo.js` —— 跑上面 3 个场景,打印"扫描行数 + 耗时"对比

## 注意

真实项目里这些是数据库的活儿,这里用内存 `Map` / 数组模拟,是为了**零依赖、聚焦逻辑**:

- 索引 → 数据库的 B+ 树二级索引(`CREATE INDEX`);这里用 `Map` 模拟"按 key 直接定位"的效果。
- 预聚合 → 定时任务把明细 `GROUP BY` 算好写进**汇总表**,看板查汇总表。
- 游标分页 → `WHERE id > :lastId ORDER BY id LIMIT 20`,沿主键索引续上,不再 `LIMIT offset, size`。

耗时数字每次跑会有波动(取决于机器和 GC),重点看**扫描行数**的数量级差距 —— 那才是慢查询的根因所在。
