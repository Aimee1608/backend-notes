# 数据库事务与隔离级别:别让"扣了 A 没加上 B"

> 转账从 A 扣了钱、没加给 B 就崩了——钱凭空蒸发；两个人同时抢最后一件库存，各自都"买到了"——超卖。这类"数据出错"，靠**事务**和**隔离级别**兜底：这篇把 ACID、四个隔离级别、以及业界靠 MVCC 和锁怎么实现，一次讲透。

---

## 一、事务是什么:ACID

**是什么。** 事务(Transaction)是**一组要么全部成功、要么全部失败的数据库操作**。它把多个操作捆成一个不可分割的整体——中间不允许停在"做了一半"的状态。

经典例子就是**转账**:A 给 B 转 100,数据库要做两件事——A 的余额 -100,B 的余额 +100。这两步必须**捆在一起**:只做第一步不做第二步,钱就凭空消失了。事务的作用,就是让这两步"同生共死"。

衡量一个事务"靠不靠谱",业界用四个公认的字母概括,就是 **ACID**。还是用转账串一遍:

| 特性 | 一句话 | 转账里对应什么 |
|---|---|---|
| **A 原子性**(Atomicity) | 要么全做,要么全不做 | 扣 A 和加 B,要么都成,要么都回滚(谁也没动) |
| **C 一致性**(Consistency) | 转完账,数据仍满足业务规则 | 转账前后,两人余额总和不变(钱不会凭空多或少) |
| **I 隔离性**(Isolation) | 并发事务之间互不干扰 | 别人这会儿查 A 的余额,不该看到我"扣了一半"的中间态 |
| **D 持久性**(Durability) | 提交后,哪怕断电也丢不了 | 一旦提示"转账成功",数据就落了盘,宕机也还在 |

**为什么。** 没有事务,这组操作就是几条独立的 SQL——第一条执行完、第二条执行前,程序崩了、机器宕了、网络断了,数据就停在了"扣了 A 没加上 B"这个**残缺状态**,而且没人帮你收拾。事务的价值,就是把这种"做一半"的风险整个消灭掉。

**这四个特性里,原子性和持久性靠的是数据库的日志机制**——典型是 **WAL**(Write-Ahead Logging,预写日志):改数据前先把"要改什么"记进日志,崩溃重启后靠日志把没做完的回滚、把已提交的补上。一致性是最终目标(由前三者+业务约束共同保证),而**隔离性是这篇的主角**——它最微妙、代价也最大,下面三节都在讲它。

> 🌰 行业里反复被讲的段子:**ATM 取钱中途断电**。钱没吐出来,但账上扣了——好的系统靠事务的原子性,要么这笔操作整个回滚(账不扣),要么补偿(后台对账退回)。你之所以很少真丢钱,正是 ACID 在底层兜着。

## 二、为什么需要隔离级别

**是什么。** 隔离级别(Isolation Level)规定了**多个事务并发执行时,一个事务能看到另一个事务"做到一半"的多少**。它是 ACID 里"I"(隔离性)的**可调档位**——之所以要分档,是因为"完全隔离"虽然最安全,却最慢。

**为什么需要。** 单个事务自己跑,没问题;一旦**多个事务同时跑**(线上几乎永远是这样),它们读写同一批数据,就会互相干扰,读到对方的半成品或被对方半路改掉的数据。业界把这些干扰归纳成三类经典问题——**脏读、不可重复读、幻读**。各用一个场景说清:

**脏读(Dirty Read):读到了别人还没提交、之后又回滚的数据。**
事务 A 把某商品库存改成 5(还没提交),事务 B 这时读到了 5,按这个数去做了决策;结果 A 回滚了,库存其实还是 10——B 读到的 5 是一个**根本不存在过的"脏"值**。脏读是最严重的,等于读到了"幻觉"。

**不可重复读(Non-Repeatable Read):同一事务里,前后两次读同一行,值变了。**
事务 A 先读了某账户余额是 100;中途事务 B 把它改成 50 并**提交**了;A 再读同一行,变成了 50。A 在一次事务里,对**同一行**读出了两个不同的结果——问题出在"别人 UPDATE 了已存在的行"。

**幻读(Phantom Read):同一事务里,前后两次按同一条件查,行数变了。**
事务 A 按条件查"价格 < 100 的商品",第一次查到 10 条;中途事务 B **插入**了一条价格 80 的新商品并提交;A 再查同样的条件,变成了 11 条——凭空多出一行,像见了"幻影"。

**幻读和不可重复读的区别**,是新手最容易混的一点,一句话点破:**不可重复读针对的是"行的内容被改了"(UPDATE),幻读针对的是"行的数量变了"(INSERT/DELETE)。** 一个是"同一行变了样",一个是"凭空多/少了行"。

| 问题 | 触发动作 | 一句话 |
|---|---|---|
| **脏读** | 读到未提交的修改 | 读到了之后会被回滚的"假数据" |
| **不可重复读** | 别人 UPDATE 了已有行并提交 | 同一行,两次读结果不同 |
| **幻读** | 别人 INSERT/DELETE 行并提交 | 同一查询条件,两次读行数不同 |

**为什么不"一律最严"。** 因为越严越慢(下一节细说)。所以数据库把"允许看到多少半成品"做成了**可选的档位**,让业务自己在"安全"和"性能"之间挑——这又是一次典型的 trade-off。

## 三、四个隔离级别

**是什么。** SQL 标准定义了四个隔离级别,从松到严依次是:**读未提交 → 读已提交 → 可重复读 → 串行化**。越往后越严,能挡住的问题越多,代价也越大。

**为什么是这四档。** 它们正好对应上一节三个问题"逐个被解决"的过程——每升一档,多挡住一类:

**① 读未提交(Read Uncommitted):最松,啥也不防。**
一个事务能读到别人**还没提交**的修改。三类问题全都可能发生,连脏读都防不住。实际几乎没人用——读到会被回滚的数据,风险太大。

**② 读已提交(Read Committed):只读"已提交"的数据,挡住脏读。**
一个事务只能读到别人**已经提交**的修改,杜绝了脏读。但同一事务里两次读之间,别人提交的 UPDATE 会被看到,所以**仍有不可重复读和幻读**。这是 **Oracle、PostgreSQL、SQL Server 等多数数据库的默认级别**。

**③ 可重复读(Repeatable Read):同一事务里,读到的数据始终如一,挡住不可重复读。**
事务一旦开始,它看到的数据就"定格"在某个版本,整个事务期间反复读同一行,结果都一样,解决了不可重复读。**这是 MySQL InnoDB 的默认级别**。
> 按 SQL 标准,这一级仍可能幻读;但 **MySQL InnoDB 靠 MVCC + 间隙锁,在大多数场景下连幻读也基本挡住了**——这是 InnoDB 的一个特色,下一节讲原理。

**④ 串行化(Serializable):最严,事务排队执行,三类全防。**
强制事务**像排队一样一个一个来**(或对读写都加锁),效果等同于没有并发。脏读、不可重复读、幻读全部杜绝,但并发能力**断崖式下降**——几乎退化成单线程,日常业务很少用,只在对一致性要求极端高的场景才考虑。

**实际业务场景。** 隔离级别不是越高越好,是按业务挑:

- **账户余额、支付**:对一致性敏感,常用读已提交起步,关键操作再配合行锁(见下节);
- **后台报表、统计**:一次事务里要多次读、且希望数据稳定,可重复读更合适;
- **绝大多数普通读写**:读已提交就够了,这也是多数数据库选它做默认的原因——**性价比最高**。

**注意一个反直觉的点:MySQL 和大多数数据库的默认级别不一样。** MySQL InnoDB 默认**可重复读**,而 Oracle / PostgreSQL / SQL Server 默认**读已提交**。换数据库、或在不同库间迁移时,这点容易埋坑——同一段代码,默认隔离级别变了,并发行为就可能变。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 谁的默认 |
|---|---|---|---|---|
| 读未提交 | ✅ 可能 | ✅ 可能 | ✅ 可能 | (几乎没人用) |
| 读已提交 | ❌ 防住 | ✅ 可能 | ✅ 可能 | Oracle / PG / SQL Server |
| 可重复读 | ❌ 防住 | ❌ 防住 | ⚠️ 标准可能,InnoDB 基本防住 | MySQL InnoDB |
| 串行化 | ❌ 防住 | ❌ 防住 | ❌ 防住 | (极少用) |

## 四、业界怎么做(原理):MVCC 与锁

上一节是"有哪些档位",这一节是"数据库怎么把这些档位实现出来"。核心就两套机制:**MVCC**(让读不加锁)和**锁**(管写、管强一致)。

### MVCC:多版本并发控制——让"读不加锁"

**是什么。** **MVCC**(Multi-Version Concurrency Control,多版本并发控制)的核心思想:**给每行数据保留多个历史版本,读的时候读某个"快照",而不是去读当下这一刻、可能正被别人改的最新值。**

**为什么能解决问题。** 因为"读"和"写"操作的是**不同版本**,所以**读不用等写、写不用等读**——读不加锁,并发能力大幅提升。事务开始时(或每条语句开始时)给它一个一致的快照:

- **读已提交**:每条**语句**开始时取一次新快照 → 所以两条语句之间能看到别人新提交的改动(这正是它"不可重复读"的来源);
- **可重复读**:整个**事务**开始时取一次快照、之后不变 → 所以一个事务里反复读,看到的始终是同一份(这正是它"可重复读"的实现)。

可以看出,**"读已提交"和"可重复读"的区别,本质就是"快照取一次还是每条语句取一次"**。这套多版本机制怎么靠"版本链 + 回滚日志"实现、和聚簇/二级索引怎么配合,属于存储引擎内部细节,可参见《查询优化》篇对索引与 B+ 树存储结构的讲解。

> 一句话:MVCC 让**读操作不加锁、读到一致的快照**,这是现代数据库高并发的基石。但它只管"读",写与写之间的冲突,还得靠锁。

### 锁:管住"写",以及强一致的读

读靠 MVCC,但**两个事务同时要改同一行**,必须有一个等另一个——这就得靠锁。锁有几个正交的分类维度,各管一摊:

**① 乐观锁 vs 悲观锁(是一种并发"思路",不只是数据库功能)。**

| | 思路 | 怎么做 | 适合 |
|---|---|---|---|
| **悲观锁** | "假设一定会冲突",先锁了再说 | 操作前先加锁(如 `SELECT ... FOR UPDATE`),别人得等 | 冲突频繁、写多 |
| **乐观锁** | "假设基本不冲突",最后提交时再检查 | 不加锁,改时带版本号 / 时间戳,提交时比对,变了就重试 | 冲突少、读多写少 |

乐观锁经典实现是**版本号法**:表里加一列 `version`,更新时 `UPDATE ... SET ..., version=version+1 WHERE id=? AND version=旧值`——如果这行已被别人改过(version 变了),这条 UPDATE 影响 0 行,说明冲突,业务层重试。它不是数据库的锁机制,而是一种**应用层的并发控制约定**。

**② 行锁 vs 表锁(锁的粒度)。**

- **表锁**:锁整张表。开销小、加锁快,但并发极差——一个事务锁了表,其他人整张表都动不了;
- **行锁**:只锁被操作的那几行。并发好得多(不相关的行照样能动),但开销和管理成本更高。
- **InnoDB 默认用行锁**(性能好);但**行锁是加在索引上的**——如果 WHERE 条件没走索引,会退化成锁全表,这是个隐蔽的坑。

**③ 共享锁 vs 排他锁(锁的"读写属性")。**

- **共享锁(S 锁 / 读锁)**:多个事务可以同时持有,大家都能读,但谁都不能写——"读读不互斥";
- **排他锁(X 锁 / 写锁)**:只能一个事务持有,持有期间别人既不能读(加锁的读)也不能写——"写和谁都互斥"。
- 规则一句话:**读读不冲突,读写、写写都冲突**。

**实际业务场景:扣库存。** 这是"什么时候用哪种锁"最典型的例子——

- **悲观锁**:`SELECT 库存 FROM ... WHERE id=? FOR UPDATE`,先把这行锁住,再扣减、提交,期间别人改不了。简单可靠,但高并发下大家排队等锁,吞吐受限;
- **乐观锁**:`UPDATE ... SET 库存=库存-1 WHERE id=? AND 库存>0`,靠 WHERE 条件保证不超卖,影响 0 行就是没扣成。冲突不极端时性能更好;真到秒杀级别的超高并发,这类直接扛在数据库上的方案都吃力,得把库存预扣搬到 Redis 等内存里(属于"高并发/秒杀"话题,这里不展开)。

> 一句话总结这节:**MVCC 管读(不加锁、读快照),锁管写(冲突时排队)**——两套配合,才撑起了"高并发下数据还不乱"。

## 五、注意事项

事务和隔离级别用对了是兜底,用错了是新的坑。几条最该记住的:

- **隔离级别越高越安全,但越慢——又是 trade-off。** 串行化最安全却几乎没并发,读已提交并发好却防不住不可重复读。别下意识"调到最高图省心",绝大多数业务读已提交 / 可重复读就够,该评估的是"我这业务到底能容忍哪类问题"。

- **长事务是头号大坑,务必避免。** 一个事务开着迟迟不提交(比如事务里夹了远程调用、人工审批、大循环),危害一连串:**① 长时间占着锁**,把别的事务全堵在后面;**② 撑大回滚段 / undo 日志**(MVCC 要保留这期间所有旧版本,删不掉),占用大量空间、拖慢整库;**③ 主从复制延迟**。一句话:**事务要短、要快,只把"必须原子"的几步放进去,别在事务里干慢活。**

- **不是所有场景都要事务、都要最高隔离。** 纯查询、统计、日志写入这类没有"一组操作要么全成"诉求的,开事务是浪费;能容忍短暂不一致的读,用低隔离换性能更划算。**按数据的重要程度分级对待,别一刀切。**

- **隔离级别只在单个数据库连接内生效。** 它管的是"一个库里多个事务并发"——**一旦操作跨了多个数据库 / 多个服务**(订单库扣库存、账户库扣余额),单机事务的 ACID 就**彻底管不着了**:两个库各自的事务无法相互感知,你没法用一个 `COMMIT` 让两边同时成功或同时回滚。

  这正是**分布式事务**要解决的问题——也是为什么这篇是它的前置。跨库怎么保证"要么都成、要么都回滚",得靠 2PC、TCC、本地消息表、Saga 等专门方案,留给架构系列「分布式事务」篇展开。**单机事务的强一致,到了分布式世界就成了奢侈品。**

- **死锁是行锁的副作用,要会防。** 两个事务各持一把锁、又互相等对方的锁,就死锁了。数据库一般能自动检测并回滚其中一个,但更该做的是预防:**让所有事务按固定顺序访问资源**(比如总是先改 id 小的行),能消掉大量死锁。

## 六、一张表

四个隔离级别能防什么、代价多大,一张表收全文:

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 并发性能 | 典型场景 / 默认 |
|---|---|---|---|---|---|
| **读未提交** Read Uncommitted | ✅ 可能 | ✅ 可能 | ✅ 可能 | 最高 | 几乎不用 |
| **读已提交** Read Committed | ❌ 防住 | ✅ 可能 | ✅ 可能 | 高 | Oracle / PG / SQL Server 默认,多数业务够用 |
| **可重复读** Repeatable Read | ❌ 防住 | ❌ 防住 | ⚠️ 标准可能 / InnoDB 基本防住 | 中 | **MySQL InnoDB 默认**,需稳定多次读的事务 |
| **串行化** Serializable | ❌ 防住 | ❌ 防住 | ❌ 防住 | 最低 | 极端强一致,罕用 |

> 读法:**从上到下越来越安全、越来越慢**。挑哪一档,看你的业务能容忍上一节哪类问题——这就是隔离级别的全部功夫。

## 名词解释

- **事务(Transaction)**:一组要么全部成功、要么全部失败的数据库操作,不可分割。
- **ACID**:衡量事务可靠性的四个特性——原子性(全做或全不做)、一致性(满足业务规则)、隔离性(并发互不干扰)、持久性(提交后不丢)。
- **WAL(预写日志)**:改数据前先把变更写进日志,崩溃后靠日志恢复;事务原子性与持久性的底层支撑。
- **隔离级别(Isolation Level)**:规定并发事务能看到彼此多少"半成品"的可调档位,是 ACID 里"隔离性"的具体落地。
- **脏读(Dirty Read)**:读到了别人尚未提交、之后又回滚的数据。
- **不可重复读(Non-Repeatable Read)**:同一事务内两次读同一行,因别人 UPDATE 并提交,结果不同。
- **幻读(Phantom Read)**:同一事务内两次按同一条件查询,因别人 INSERT/DELETE 并提交,行数不同。
- **读未提交 / 读已提交 / 可重复读 / 串行化**:SQL 标准的四个隔离级别,从松到严,依次多挡住一类并发问题。
- **MVCC(多版本并发控制)**:给每行保留多版本,读取一致快照而非最新值,使读不加锁、读写不互相阻塞;现代数据库高并发的基石。
- **快照(Snapshot)**:事务/语句开始时数据的一致视图;读已提交每条语句取一次,可重复读整个事务取一次。
- **乐观锁 / 悲观锁**:并发控制的两种思路——乐观锁假设少冲突,提交时用版本号比对、冲突重试;悲观锁假设会冲突,操作前先加锁。
- **行锁 / 表锁**:锁的粒度——行锁只锁相关行(并发好,InnoDB 默认,加在索引上),表锁锁整张表(开销小但并发差)。
- **共享锁(S)/ 排他锁(X)**:共享锁可多事务同时持有(读读不互斥),排他锁独占(读写、写写都互斥)。
- **长事务**:开启后长时间不提交的事务,会长时间占锁、撑大回滚段、加剧主从延迟,应尽量避免。
- **死锁(Deadlock)**:两个事务互相等待对方持有的锁,谁都进行不下去;靠固定加锁顺序预防,数据库可自动检测回滚。
- **分布式事务**:跨多个数据库/服务时保证"要么都成、要么都回滚"的机制(2PC / TCC / 本地消息表 / Saga 等),单机事务的 ACID 管不了——详见架构系列「分布式事务」篇。
