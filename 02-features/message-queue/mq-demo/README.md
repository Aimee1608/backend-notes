# 消息队列 demo:解耦 / 防丢 / 幂等 / 顺序(零依赖)

配套文章:《消息队列:为什么要 MQ,以及丢失、重复、顺序怎么破》

这个 demo **不用装 Kafka / RabbitMQ** —— 用内存模拟一个最小可用的 MQ
(produce / consume + 手动 ack + 失败重投 + 分区),
聚焦把消息队列最该懂的几件事**用对比结果直观看出来**。

## 怎么跑

```bash
node demo.js
# 或
npm start
```

跑完即退出,无任何外部依赖。

## 演示了什么

| 场景 | 主题 | 机制 | 看什么 |
|---|---|---|---|
| 一 | 异步解耦 | 一条消息,多下游各取所需 | 下单发完即返回,短信 / 积分各自消费 |
| 二 | 防丢失 | 处理完再 ack + 失败重投 | 崩溃没 ack → 消息重投,总投递次数 > 1,最终不丢 |
| 三 | 重复消费 + 幂等 | 业务唯一键去重 | 同一消息投两次:无幂等积分 100(错),有幂等 50(对) |
| 四 | 顺序 | 分区路由 | 多分区并行 → 顺序乱;同 key 同分区 → 严格有序 |

## 文件

- `lib.js` —— 内存版 MQ broker(分区、手动 ack、失败重投、死信)+ 幂等去重工具(带中文注释)
- `demo.js` —— 跑上面 4 个场景,打印对比

## 注意

真实项目里 MQ 用 **Kafka / RabbitMQ / RocketMQ** 等,这里用内存数组模拟,是为了**零依赖、聚焦逻辑**。
换成真实 MQ 时思路一一对应:

- `produce` → 生产者发送(开 confirm/ack 确保到达 broker)
- `consumePartition` 的"处理完才 ack" → 消费端手动 ack(`auto-commit=false`)
- 失败 `requeue` / 死信 → broker 的重试与死信队列(DLQ)
- 按 key 选分区 → topic 的 partition 路由(同 key 同分区,保证分区内有序)
- `IdempotencyGuard`(内存 Set)→ 数据库唯一索引 / Redis 去重表
