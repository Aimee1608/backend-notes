## 2. 基本盘:认证 vs 授权,Session vs Token

**先分清两个词:**
- **认证 (Authentication)**:你是谁?—— 证明身份(登录)
- **授权 (Authorization)**:你能干什么?—— 有没有权限访问某个资源

**两种实现思路对比:**

| | Session-Cookie | Token (JWT) |
|---|---|---|
| 状态存哪 | 服务端存 session,客户端存 sessionId | 服务端不存,token 自带信息 |
| 水平扩展 | 多机要共享 session(如 Redis) | 无状态,天然好扩展 |
| 跨域/多端 | Cookie 跨域麻烦 | 带 header 即可,App/小程序友好 |
| 注销 | 删 session 即时失效 | 签发后难即时失效(需额外机制) |

## 3. OAuth 2.0:两种最常见的拿 token 场景

OAuth 2.0(RFC 6749)是业界标准,两种最常见的 grant:

**① 用户授权 —— Authorization Code**
用户在授权页点"同意",应用拿到授权码,再换成 token。典型场景:"用 GitHub 账号登录某网站"。

**② 服务间调用 —— Client Credentials**
没有用户参与,一个服务用自己的 `client_id + client_secret` 换 token,去调它有权限的接口。典型场景:后端服务之间互调。

**JWT 在里面是什么角色?**
JWT(RFC 7519)是 token 的一种**自包含**格式:本身就带身份(`sub`)和权限(`scope`),还有签名防篡改。服务端不用查库,验签 + 读 claims 就知道"你是谁、能干啥"。

## 5. 关键点 & 我踩的坑

公开标准里的几个要点(我已列出,你补充自己实操的体会):
- **access token 要短命**:泄露了窗口也小;靠 refresh token 悄悄续。
- **refresh token 要能撤销**:存一份 allow-list(demo 用内存 Set,生产用 Redis),注销/轮转时删掉。
- **token 轮转 (rotation)**:每次 refresh 换一对新的、旧的作废,降低泄露风险;也是"长期不操作才要求重新登录"(滑动过期)的实现基础。
- **JWT 别塞敏感信息**:它只是 base64 编码、**不是加密**,谁都能解开看内容。
- **注销难题**:无状态 JWT 签发后,过期前难即时失效 —— 靠短 TTL + 黑名单/allow-list 兜底。
