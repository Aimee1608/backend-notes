# 从 Prompt Engineering 到 Context Engineering：变的不只是名字

三年前，做 LLM 应用最热的技能叫 **Prompt Engineering**：怎么把一句话写得让模型听懂、答好。现在这个词在技术讨论里明显退潮了，取而代之的是 **Context Engineering**。

这不是换个时髦叫法。它反映的是一个实际变化：**现代 LLM 应用送进模型的东西，早就不是"一句话"了**。这篇讲这个变化是什么、为什么发生、对你写应用意味着什么。

---

## 模型看到的到底是什么

回到第 09 篇的请求结构。一个真实的生产应用，一次请求里模型读到的内容通常包括：

1. **System 指令**：你是谁、规则是什么、输出什么格式
2. **工具定义**：可以调哪些接口、每个接口的参数是什么（Agent 场景下这部分可能有几千上万 token）
3. **检索结果**：从知识库、搜索引擎、数据库里捞出来塞进去的材料
4. **记忆**：跨会话的用户偏好、之前任务的摘要
5. **对话历史**：这个会话里之前所有的来回，包括之前工具调用的结果
6. **本轮用户输入**：用户刚刚打的那句话

用户打的那句话，往往只占整个输入的百分之几。**模型的输出质量，是这六块内容共同决定的**，不是第六块单独决定的。

"Prompt Engineering"这个词的隐含假设是：效果 = f(那句话)。而现实是：效果 = f(整个上下文)。这就是为什么词要换——它指向的对象变了。

---

## 为什么以前那套不够用了

早期应用简单：一个 system 提示加一句用户输入，模型直接回答。那时候"把这句话写好"确实是效果的主要杠杆。

三个变化让这个假设失效：

**上下文变长了**。窗口从几千到百万（第 11 篇），能塞的东西多了，塞什么、怎么排、塞多少，成了新的决策空间。

**工具调用成了常态**。Agent 每一步都要读全部工具定义和之前所有步骤的结果，上下文在循环里持续膨胀。这里的问题不再是"这句话怎么写"，而是"几十步之后上下文里应该留什么"。

**模型变强了**。指令遵循能力大幅提升后，措辞技巧（"请务必""你是一位资深专家"）的边际收益急剧下降。以前措辞不当模型就跑偏，现在把意思说清楚它就能做对。杠杆从"怎么说"转移到了"给它看什么"。

一句话概括：**模型不再需要被哄，但需要被喂对东西**。

---

## Context Engineering 在做什么

把它拆成四个动作：

### 一、选择：什么该进上下文

不是所有相关信息都该塞进去。判断标准是"这条信息会不会改变模型的输出"——会，就进；不会，就是噪声。检索出 20 条结果只有 3 条相关，塞 20 条不如塞 3 条（第 11 篇的注意力稀释）。

### 二、组装：进来的东西怎么排

顺序有影响。稳定内容放前面、可变内容放后面，这是缓存命中的前提（第 10 篇）。关键信息靠近问题位置，不要埋在中间（第 11 篇）。各部分用清晰的边界分隔——模型需要知道"这段是文档、那段是指令、这段是工具返回"。

### 三、压缩：太长了怎么办

长对话和 Agent 循环里，上下文单调增长是默认行为，必须主动干预：把早期历史摘要成一段、把已经用完的工具返回清理掉、把大段原始数据换成结论。目标是**保留决策需要的信息，丢掉过程产生的垃圾**。第 25 篇专门讲。

### 四、隔离：不该混在一起的分开

不同任务用不同上下文。一个 Agent 要同时做"搜索资料"和"写报告"，让一个上下文承担两件事，两件事都会被对方的中间产物干扰。拆成两个子任务、各自独立上下文、只传递结论，效果和成本都更好。多 Agent 架构的核心动机之一就是这个。

## 一个直观的类比

把模型想象成一个能力很强、但**每次上班都失忆**的新员工。

Prompt Engineering 是琢磨"怎么跟他说话他才听得懂"。三年前这很重要，因为他理解能力有限。

Context Engineering 是琢磨"他上班时桌上该放什么材料"——项目背景、相关文件、上次的进度、可以找谁帮忙。他现在理解能力很强，你说清楚他就能干；真正决定他干得好不好的，是桌上的材料对不对、够不够、有没有堆了一桌子无关的东西。

材料放对了，一句简单的"把这个做完"就够。材料不对，措辞再精心也没用。

---

## 对写应用的直接影响

- **设计输入的时候，把六块内容都当成设计对象**。system 指令只是其中一块，工具定义的措辞、检索结果的格式、历史的截断策略，同等重要。
- **效果差先查上下文，再改措辞**。多数"模型答不好"的案例，根因是它没看到该看的信息，或者看到了太多不该看的。
- **把上下文当成有成本的资源**。每个 token 都在计费、都在稀释注意力、都在拉长延迟。往里放东西要有理由。
- **可观测性要覆盖上下文**。线上出问题时，你得能看到"那次请求模型到底读了什么"，不然无从排查。第 31 篇讲。
