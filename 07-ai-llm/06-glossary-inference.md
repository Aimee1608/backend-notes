# 推理采样词扫盲：模型生成一个字的背后

为什么同一个问题问两次，答案不一样？为什么 Temperature 设为 0 还是可能有差异？KV Cache 又是什么，为什么它能省钱？

这组词都指向同一个环节：**模型生成每一个 token 的瞬间，发生了什么**。看懂这个瞬间，这些参数就不再是玄学旋钮。

---

## Logits：生成前的原始分数

模型处理完输入后，并不直接吐出一个词。它输出的是**词表里每个 token 的原始得分**——这组分数叫 Logits。

词表通常有十几万个 token，所以每生成一个字，模型内部实际产出的是一张十几万行的评分表："下一个 token 是'的'，得分 12.3；是'了'，得分 11.8；是'香蕉'，得分 -5.2……"

从这张评分表到最终选出一个 token，中间要经过采样——下面这堆参数，全是在控制"怎么从评分表里选"。

---

## 贪心解码：永远选最高分

最朴素的策略：每次都选得分最高的那个 token。这叫**贪心解码（Greedy Decoding）**。

确定性强（同样输入基本同样输出），但生成质量往往不好——每步都选局部最优，容易陷入重复啰嗦的循环（"非常非常非常好"），也让文本呆板。所以实际生成默认都用带随机性的采样，贪心只在需要严格确定性的场景用。

---

## Temperature：随机程度的总开关

采样前，先把 Logits 换算成概率分布，**Temperature 控制这个分布的"尖锐程度"**：

- **低温（趋近 0）**：分布变得极尖，高分 token 概率被放大到接近 1——基本等于贪心，输出稳定
- **温度 1**：按模型原始的概率分布采样
- **高温（>1）**：分布被压平，低分 token 也有可观的机会被选中——输出多样但容易跑飞

场景对应很直接：抽取、分类、代码生成用低温（要稳定）；创意写作、头脑风暴用中高温（要多样）。

一个常见误解：**Temperature = 0 也不保证 100% 复现**。GPU 并行计算的浮点误差、服务端的批处理调度，都可能让两次运行产生细微差异。要把"温度 0"理解为"尽量稳定"，不是"严格确定"。

---

## Top-k 与 Top-p：先划范围再采样

纯按概率采样有个隐患：词表长尾里几万个低分 token，单个概率虽小，加起来不小——总有一定机会采出一个完全离谱的词。所以要先把候选范围切小：

- **Top-k**：只保留得分最高的 k 个 token（如 k=50），其余全部清零，再在这 50 个里采样
- **Top-p（核采样）**：把 token 按概率从高到低累加，加到总和达到 p（如 0.9）为止，只保留这部分。它比 Top-k 聪明的地方：候选数量随分布自动伸缩——模型很确定时（第一名概率 0.95）候选只剩一两个，模型犹豫时（概率摊得平）候选自动放宽

实用建议：**Temperature 和 Top-p 一般只调一个**，两个都动很难归因效果变化。多数场景动 Temperature 就够了。

---

## Max Tokens 与 Stop Sequence：什么时候停笔

- **Max Tokens**：本次生成的 token 上限。到了就硬截断——注意是"掐断"不是"收尾"，超限的输出会在半句话处戛然而止。做结构化输出时尤其要留够余量，JSON 生成一半被截断是经典事故。
- **Stop Sequence**：自定义停止符。生成内容一旦出现指定字符串就立刻停止。适合"只要第一段"、"生成到某个标记为止"这类控制。

模型自己也会停——生成出一个特殊的"结束 token"（训练时学会的"我说完了"信号）。三种停止条件谁先触发听谁的。

---

## KV Cache：为什么长对话不会越来越慢

自回归生成的机制是：每生成一个新 token，都要"看一遍"前面所有内容。按理说第 1000 个 token 要重新计算前 999 个的信息——越写越慢，成本平方级爆炸。

**KV Cache** 就是解法：前文每个 token 算过的中间结果（Attention 机制里的 Key 和 Value）缓存下来，生成新 token 时直接复用，不重算。这是所有推理引擎的标配优化，没有它长文本生成根本不可行。

它的延伸就是你账单上的 **Prompt Cache**：既然中间结果可以缓存，那多次请求之间也能复用——只要请求的前缀完全相同（比如固定的 System Prompt + 工具定义），这部分的计算直接跳过。这就是缓存命中的输入 token 便宜一个数量级的原理，也是为什么优化缓存命中率要"把固定内容放前面，可变内容放后面"。

---

## 投机采样（Speculative Decoding）：小模型打草稿，大模型批卷

大模型生成慢的根源：每个 token 都要过一遍完整的大模型。投机采样的思路很妙：

1. 让一个小模型快速"猜"出接下来的几个 token（草稿）
2. 大模型**一次性并行验证**这几个 token 对不对
3. 猜对的部分直接采纳，猜错的位置由大模型修正，然后继续

因为验证可以并行而生成必须串行，小模型猜得准的时候，速度能提升数倍——而且**数学上保证输出分布和大模型完全一致**，不是"用小模型凑合"。

这是服务端的优化技术，API 用户感知不到细节，但"这家的模型怎么突然变快了"背后经常有它。

---

## 收个尾

把这组词串起来：模型每一步产出评分表（Logits），Temperature/Top-p 决定怎么从表里选（采样），Max tokens/Stop 决定何时停，KV Cache 让长文本不至于越算越慢，投机采样让整个过程再提速几倍。

"同一个问题答案不一样"的答案也在其中：采样本身带随机，这是设计使然。需要稳定就压低 Temperature——但要记住，那也只是"尽量稳定"。
