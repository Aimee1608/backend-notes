# 强模型时代，System Prompt 还要精心雕吗

三年前流传的 system prompt 模板长这样：先封一个头衔（"你是一位拥有 20 年经验的资深架构师"），再念一段咒语（"请深呼吸，一步步思考，这对我的职业生涯非常重要"），最后堆上十几条"务必""绝不"。

这些东西现在还有用吗？一部分彻底没用了，一部分比以前更重要了。这篇把 system prompt 拆开，说清楚哪些该省、哪些不能省。

---

## 先明确 system prompt 是什么

它是应用开发者写给模型的**常驻指令**，每次请求都在，用户看不到。它定义的是这个应用里模型的行为边界，而不是某一次对话的内容。

用第 13 篇的框架：它是上下文六块里的第一块，通常也是最稳定的一块——这决定了它应该放在最前面（缓存命中），也决定了它的措辞会影响每一次请求。

---

## 可以省的

### 花哨的角色扮演

"你是世界顶级的 XX 专家"这类开场，早期确实有用：那时模型的能力需要被"激活"，一个专家身份能让它调用更专业的表达方式。

现在的模型不需要这个。它的默认能力已经是"专家水平"，加个头衔不会让它更专业，只会多占几十个 token。角色设定还有用的场景只剩一个：**产品需要一个特定的人设**（客服叫小 A、语气要活泼），那是产品需求，不是提升能力的手段。

### "深呼吸""一步步想"类咒语

第 02 篇讲过，"一步步思考"是在手动触发思维链。推理模型已经把这个能力内化了，开思考模式比念咒有效得多，不开思考模式的场景本来也不需要推导。

"这对我很重要""你会得到小费"这类情绪激励，在早期模型的某些测试里有过微弱效果，现在基本测不出差异了。留着不会坏事，但它们是迷信不是工程。

### 长篇大论的"务必""绝不"

十几条互相重叠的禁令，模型会照做，但每条都在占注意力。现代模型的指令遵循能力强到"说一遍就够"，重复强调不会让遵循率更高，反而可能让它过度谨慎——该回答的也不敢答。

---

## 不能省的

### 行为边界

这个应用里模型**能做什么、不能做什么**。客服机器人能不能承诺退款、能不能提竞品、遇到投诉怎么处理。这些是业务规则，模型不可能自己知道，必须写清楚。

写法上，**说清楚"做什么"比"怎么做"重要**。"用户问价格时，报官网价格并说明可能变动"，比"作为一名专业客服你应该谨慎对待价格问题"有效得多。前者是可执行的规则，后者是让模型猜。

### 输出契约

模型的输出会被谁消费？是人看，还是代码解析？如果是代码解析，格式必须精确约定——字段、类型、什么情况下返回什么。这部分现在有更好的工具（第 15 篇的结构化输出），但 system prompt 里依然要说明输出的**语义**：每个字段代表什么、空值怎么表示、不确定时怎么标记。

### 拒绝策略

超出范围的请求怎么处理。不写的话，模型会用它的默认行为——通常是尽力回答，哪怕这个问题和你的应用毫无关系。写清楚"不在范围内的问题，礼貌说明只能处理 XX 类问题"，比出了事再补要便宜得多。

拒绝策略也包括**不确定时怎么办**。是猜一个答案，还是明确说不知道，还是转人工？不同业务的容错完全不同，模型不该替你做这个决定。

### 上下文的说明

第 13 篇讲的六块内容，模型需要知道每块是什么。"下面 <documents> 标签里的是检索到的资料，回答要基于这些资料，资料里没有的说不知道"——这句话决定了模型是把检索结果当权威来源还是当参考，效果差很多。

---

## 现在的 system prompt 长什么样

一个合格的现代 system prompt，结构大致是：

1. **一句话定位**：这是什么应用，模型在里面扮演什么角色（功能性描述，不是头衔）
2. **任务规则**：核心业务逻辑，用可执行的语言写，按场景分条
3. **边界与拒绝**：什么不做、遇到范围外的请求怎么回
4. **输出要求**：格式和语义
5. **上下文说明**：后面各部分内容是什么、怎么用

长度以说清楚为准。几百 token 到几千 token 都正常，但每一句都应该是"删掉会出问题"的。删掉不会出问题的，就是该删的。

---

## 一个检验方法

把你的 system prompt 给一个不了解业务的同事看，问："照这个去做，你知道该怎么做吗？"

他能照着做，模型也能。他看完一头雾水（"什么叫'谨慎处理'？"），模型也在猜。**system prompt 的本质是给一个能力很强但不了解你业务的人写的工作说明**，写工作说明的标准就是写它的标准——清楚、具体、可执行，不需要修辞。
