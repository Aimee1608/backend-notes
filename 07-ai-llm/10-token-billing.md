# Token 计费：输入、输出、思考、缓存，四种价

三年前看模型账单，两个数：输入多少钱、输出多少钱。现在打开任何一家的定价页，一个模型一行里能有五六个数：输入、输出、缓存写入、缓存读取、批量折扣……再加上思考模式的 token 该算哪一栏。

账单结构变复杂了，但底层逻辑很清楚。这篇把每一栏对应到请求链路里的哪一步，你就能看懂自己的账单从哪来。

---

## 先搞清 token 是什么

模型不按字、也不按词计数，按 **token**。token 是分词器（tokenizer）切出来的单元，主流做法叫 **BPE（Byte Pair Encoding）**：从字节级别开始，把语料里高频共现的片段逐步合并成一个单元，最终形成一张十几万条目的词表。常见英文单词往往一个 token，生僻词会被拆成几段；中文里一个常用字通常一到两个 token，一个成语可能是一个 token 也可能是四个。

对研发有用的几个推论：

- **中英文成本不同**。同样意思的一段话，中文的 token 数往往比英文多。做粗估时，中文按"一字一个 token 出头"、英文按"一个词 1.3 个 token 左右"。
- **不同厂商的分词器不同**。同一段文本，A 家算 1000 token，B 家可能算 1200。跨厂商比价，要把分词差异也算进去。
- **同一厂商换代也可能换分词器**。新模型 token 数变了不是错觉，压测时要用新模型重新算。
- **精确计数用官方的 count 接口**，各家都有。别用第三方库估——分词器版本对不上，误差可以到两位数百分比。

## 账单的四栏

### 一、输入（Input）

请求体里模型读进去的全部内容：system 指令、对话历史、你塞进去的文档、工具定义、图片（图片按分辨率折算成 token）。这是最基础的一栏，也通常是**总量最大**的一栏——因为多轮对话每一轮都重发全部历史（第 09 篇），Agent 场景里工具定义和工具结果也在这里反复出现。

### 二、输出（Output）

模型生成的内容。**单价通常是输入的几倍**——生成是逐 token 串行的，比并行读入贵得多，价格反映的是算力成本。

一个常见误判：输出 token 数量比输入少得多，所以觉得输出不是大头。但乘上单价后，一个"读 5000 输出 500"的请求，输出费可能和输入费一样多。压成本时别只盯输入。

### 三、思考（Thinking）

推理模式下模型生成的推理过程。**全部按输出价计费**——它就是模型生成的 token，只是没展示给你。

这一栏的特点是**不可见但不便宜**：一个简单问题开了思考模式，思考部分可能是正文的几倍到几十倍长度，账单上体现为"输出 token 莫名其妙很多"。第 02 篇的结论在这里再重复一遍：按接口分级开思考，不要全局开。

### 四、缓存（Cache）

这是三年里新增的一栏，也是最需要理解的一栏。

原理第 06 篇讲过：模型处理输入的中间结果可以缓存，**只要新请求的前缀和之前某次请求完全相同**，这部分就不用重算。厂商把省下的算力以折扣返还给你——命中缓存的输入 token 按缓存价计，通常是正常输入价的**一到五折**（各家不同）。

各家在缓存上的差异集中在三点，看定价页时对号入座：

- **写入要不要收费**：有的厂商缓存写入按正常输入价的一点几倍收（你为"存下来"付溢价），有的自动缓存不收写入费
- **要不要你显式标记**：有的要在请求里标缓存断点，有的自动检测最长匹配前缀
- **缓存活多久**：几分钟到一小时不等，有的可以花钱延长，有的按存储时长另收费

无论哪种，判断缓存有没有生效只看一处：**响应 usage 里的缓存命中字段**。连续同类请求命中数一直是零，说明前缀被什么东西打破了——system 里塞了当前时间戳、工具列表顺序不固定、每次请求都改了开头的某个字。缓存是前缀匹配，**前面改一个字，后面全部失效**。

## 一次请求的成本公式

用文字写出来：

> 成本 = 未命中的输入 × 输入价 + 命中缓存的输入 × 缓存价 + 缓存写入 × 写入价（如果收） + （正文输出 + 思考）× 输出价

再乘上场景放大系数：

- **多轮对话**：每轮重发全部历史，输入随轮次线性增长。第 N 轮的累计输入 ≈ 前面所有轮次内容之和。这是缓存最能发力的地方——历史前缀每轮都一样，命中率理论上可以很高
- **Agent 循环**：一个任务跑十步，就是十次请求，每次都带全部工具定义和之前所有步骤的结果。**步数是成本放大器**，第 27 篇专门讲
- **长文档直塞**：把一份大文档放进上下文，每次问一个问题都为整份文档付一次输入费。要么靠缓存摊薄，要么改用检索（第四章）

## 一个能落地的判断

看到"账单高"，先拆哪一栏：

- **输入占大头** → 看缓存命中率，看历史是否该截断，看有没有把不必要的内容（冗长的工具描述、整篇文档）反复塞进去
- **输出占大头** → 看思考模式是不是全局开了，看有没有让模型输出了大量不需要的内容（完整复述输入、啰嗦的解释）
- **两者都不高但总额高** → 看请求次数，多半是 Agent 步数或重试失控

这个拆法的前提是**usage 有记日志**。每次响应的 usage 字段写进日志、按接口维度聚合，是 LLM 应用上线前必须做的基础设施，没有它所有成本优化都是盲猜。
