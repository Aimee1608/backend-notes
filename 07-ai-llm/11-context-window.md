# 上下文都 1M 了，还会有什么问题

三年前上下文窗口是 4K、8K，"塞不下"是每天都要面对的限制。现在主流模型的窗口普遍到了百万 token 量级，能装下一整本书、一个中型代码库。

于是一个自然的想法：既然都能塞下，那就全塞进去，让模型自己找。这篇讲为什么这个想法不成立——**窗口变大解决的是"能不能放进去"，没解决"放进去之后模型能不能用好"**。

---

## 窗口是什么

上下文窗口是一次请求里模型能处理的 token 总量上限，**输入和输出共享**。窗口 1M，塞了 990K 的输入，输出就只剩 10K 的空间。

它的技术含义是：模型在生成每一个 token 时，能"看到"的内容范围。窗口内的每个 token，都参与对下一个 token 的预测计算——这是注意力机制在做的事。理解了"每个 token 都参与计算"，下面的问题就都好理解了。

---

## 问题一：中间遗忘（Lost in the Middle）

一个被反复验证的现象：把关键信息放在长输入的**开头或结尾**，模型答得好；放在**中间**，准确率明显下降。曲线是 U 形的——两头高、中间低。

原因和训练数据分布有关：自然文本里，重要信息倾向出现在开头（标题、摘要）和结尾（结论），模型学到了这个先验。也和注意力的数学性质有关：位置越靠近当前生成点，权重天然越高。

新一代模型在这个问题上有改善，但没有消失。厂商公布的"大海捞针"测试（在长文本里藏一句话让模型找）高分，说明模型**能定位**一句孤立的信息；它不说明模型能对散落在中间的多段信息做**综合推理**。前者是检索，后者是理解，两者的难度差了一个量级。

---

## 问题二：注意力稀释

窗口里内容越多，每一段分到的"注意力"越少。往上下文里塞十份不相关的文档，问其中一份的问题，模型要在十倍的噪声里找信号。实测规律是：**无关内容越多，回答质量越差**——即便相关内容一字不少。

这在 Agent 场景里尤其明显。一个跑了几十步的 Agent，上下文里堆满了早期工具调用的原始返回（大段 JSON、日志、网页正文），真正和当前决策相关的可能只有最后几步。模型不是不看，而是看的时候被大量陈旧信息干扰，开始"跑偏"——引用早已过时的中间结果、重复做过的操作。这就是为什么现代 Agent 框架普遍做**上下文清理**：定期把旧的工具结果清掉或摘要掉，不是为了省钱，是为了保持模型的判断力。

---

## 问题三：成本放大

第 10 篇的公式在这里直接生效：**窗口里的每个 token，每次请求都要付费**。

塞一份 500K 的文档进去问一个问题，这一次请求为 500K 输入付费。问十个问题，付十次。多轮对话里更狠——文档每一轮都在历史里重发。缓存能摊薄（前缀相同的部分打折），但缓存有生存时间，间隔一长就要重新写入，写入本身还可能有溢价。

对比一下：先从文档里检索出和问题相关的 5K，只把这 5K 放进上下文——输入是前者的百分之一。窗口大了不等于用满是免费的。

---

## 问题四：延迟

输入 token 要被完整读一遍才开始生成，**首字延迟（TTFT）和输入长度正相关**。几千 token 的输入首字几百毫秒，几十万 token 的输入首字可能要十几秒甚至更久。在线对话场景里这是直接的用户体验损失；一个"每轮都带着整本手册"的客服机器人，每句话都要让用户等。

---

## 那该怎么用

结论不是"别用长上下文"，是**塞得进 ≠ 应该塞**。实用的判断：

**用长上下文直塞的场景**：一次性任务（读一份合同抽条款、审一个 PR）；内容之间有强关联、切开会丢信息（一份长报告的前后逻辑）；总量在几万到十几万 token、且要问的问题需要通览全文。这些场景下长窗口是真正的能力提升，三年前做不到。

**不该直塞的场景**：语料远超窗口、只有一小部分和当前问题相关（企业知识库）；内容频繁变化（实时数据）；不同用户能看的范围不同（权限）；同一份内容要被高频反复询问（成本）。这四条是第 17 篇 RAG 决策树的核心。

**不管塞多少，都值得做的**：

- 把最关键的内容放在开头或紧挨着问题的位置，别埋在中间
- 长对话和 Agent 场景做**压缩**（老历史摘要成一段）或**清理**（删掉过期的工具结果），不要让上下文单调增长
- 关注 usage 里的输入 token 数，它涨得比预期快就是信号

---

## 一句话版本

窗口大小是模型的**容量**，不是模型的**理解力**。容量的提升让很多原来做不了的事变得可行，但"全塞进去"依然要为中间遗忘、注意力稀释、成本和延迟买单。会选择往里放什么，比能放多少更重要。
