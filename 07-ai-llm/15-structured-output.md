# 结构化输出：现在是原生能力，别再自己解析了

后端接 LLM，十有八九不是让它聊天，是让它**产出程序能用的数据**：从工单里抽字段、给评论打标签、把自然语言转成查询条件。这些场景的共同要求是：输出必须是严格的结构，代码要能直接解析。

三年前这是个苦活。现在它是 API 的原生能力。这篇讲老做法错在哪、新做法怎么用、schema 怎么设计才不踩坑。

---

## 老做法：求模型返回 JSON

早期的标准操作：在 prompt 里写"请以 JSON 格式返回，包含 name、phone、issue 三个字段，不要输出其他内容"。然后代码里：

- 先正则把 Markdown 代码块的 ``` 剥掉
- 再试着 JSON.parse
- 解析失败就重试，或者用一堆启发式规则修补（补引号、去尾逗号）
- 解析成功还要校验字段齐不齐、类型对不对

问题不在麻烦，在**不可靠**。模型是概率生成的，"请返回 JSON"是一个请求不是一个约束。它多数时候照做，偶尔会在前面加一句"好的，以下是结果："，偶尔漏个字段，偶尔把数字写成字符串。百分之一的失败率，在日调百万的系统里就是一万次事故。

---

## 新做法：让 API 保证格式

主流厂商现在都提供**原生的 schema 约束**：你在请求里给一个 JSON Schema，API 保证返回的内容一定符合这个 schema。

各家的接法略有不同——有的是响应格式参数，有的挂在工具定义上（定义一个工具、参数就是你的 schema、要求模型必须调它），有的两种都有。名字也不同（Structured Outputs、JSON Schema mode、response schema）。但底层机制是一样的：**约束解码（Constrained Decoding）**。

原理回到第 06 篇：模型每一步生成都是从词表评分里采样。约束解码在采样前先把"不符合 schema 的 token"全部屏蔽掉——当前位置按 schema 只能是引号或右花括号，那其他几万个 token 的概率直接归零。模型不是"被要求"输出合法 JSON，而是**在生成层面不可能输出非法 JSON**。

这意味着三件事：

- **解析不会失败**。不用剥代码块、不用修补、不用重试
- **字段和类型有保证**。schema 里标了 required 的字段一定在，标了 integer 的一定是整数
- **成本不变或更低**。约束在采样层做，不额外消耗 token；省掉的是重试和修补的成本

---

## 保证的是格式，不是正确

这是新做法最容易被误解的地方：**schema 约束保证输出合法，不保证输出正确**。

抽一个电话号码，schema 要求 string，模型可以返回一个合法的字符串，内容是错的。分类打标签，schema 用枚举限定了五个类别，模型一定返回其中一个，但可能选错。

约束解码解决的是"格式事故"，不解决"理解错误"。后者依然要靠上下文质量（第 13 篇）、任务描述清晰度和评估（第 31 篇）。别因为格式稳了就把校验全撤掉——业务层面的合理性校验（手机号是 11 位数字、金额不为负）还是要有。

---

## Schema 设计影响输出质量

同一个任务，schema 怎么写，模型答得好坏差很多。几条经验：

**字段名和描述是给模型看的提示**。`field1` 和 `customer_complaint_category` 对模型来说完全不同，后者本身就在告诉它这个字段该填什么。每个字段的 description 要写，写成"这个字段应该是什么"的说明。

**用枚举替代自由字符串**。分类任务，`category: string` 让模型自由发挥，会出现"投诉""客诉""用户投诉"三种写法；`category: enum ["投诉", "咨询", "建议"]` 一次性解决。能穷举的都穷举。

**给"不确定"留位置**。强制模型从固定选项里选，它会硬选。加一个 `"其他"` 或 `"无法判断"` 选项，或者让字段可空，模型才有诚实的出口。否则你拿到的是看起来很确定的错误答案。

**字段顺序影响推理**。生成是顺序的，前面的字段会成为后面字段的上下文。把"推理依据"放在"结论"前面，模型会先写依据再下结论，准确率通常更高；反过来先写结论，依据就成了事后找补。

**别嵌套太深**。三四层的嵌套对象，模型容易在深层丢失全局视角。能拍平就拍平，复杂结构考虑拆成多次调用。

**schema 越大，约束越重**。几十个字段的巨型 schema，模型要同时照顾的东西太多，单个字段的质量会下降。一次抽一组相关字段，比一次抽全部更稳。

---

## 失败兜底

格式不会失败了，还有什么会失败：

- **撞输出上限**。schema 约束下输出到一半被 max_tokens 掐断，拿到的是半截 JSON——这时约束也救不了。第 06 篇的提醒：max_tokens 要留够余量，看 stop_reason
- **模型拒答**。触发安全策略的请求，返回的可能是拒绝说明而不是结构化数据，同样看 stop_reason
- **内容不合理**。格式对、内容错。靠业务校验兜底，校验不过按业务规则处理（重试、降级、转人工），不要无限重试——每次重试都花钱

处理链路：检查 stop_reason → 解析（这一步现在不会失败） → 业务校验 → 校验失败走兜底。比老做法少了一半环节，剩下的环节更清晰。

---

## 什么时候不用

需要模型**自由发挥**的场景——写文章、开放式回答、创意生成——不要套 schema。约束解码会限制表达，把一篇文章塞进 `{"content": "..."}` 没有意义。结构化输出是给"程序消费"的场景用的，人看的输出让它自然生成。
