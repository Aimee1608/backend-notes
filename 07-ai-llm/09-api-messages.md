# 怎么调 API：messages 结构长什么样

前面八篇讲的是"模型是什么"，从这篇开始讲"怎么用"。

所有 LLM 应用，不管上层包了多少框架，最底下都是同一件事：**发一个 HTTP 请求，带上一段结构化的对话，收一个结构化的回复**。这个请求响应的结构，是后面所有内容（计费、上下文、工具调用、Agent）的地基。这篇把它拆开看清楚。

---

## 一次请求的骨架

各家的字段名略有出入，但骨架高度一致：

```json
{
  "model": "要用哪个模型",
  "system": "给模型的全局指令",
  "messages": [
    { "role": "user", "content": "用户说的话" },
    { "role": "assistant", "content": "模型上一轮的回答" },
    { "role": "user", "content": "用户这一轮说的话" }
  ],
  "max_tokens": 4096
}
```

四个核心部分：用哪个模型、全局指令、对话历史、输出上限。其余全是可选项：采样参数（第 06 篇讲过的 Temperature 那组）、思考模式开关、工具定义（第 22 篇）、输出格式约束（第 15 篇）。

先记住一个事实：**模型收到的就是这一坨**。它没有别的信息来源——没有你的数据库、没有上一次请求、没有"账号记忆"。这个请求体里有什么，模型就知道什么。

---

## 三个角色

`messages` 里的每条消息都有一个角色，三种：

**system（系统）**：应用开发者写给模型的规则——你是谁、要做什么、不能做什么、输出什么格式。用户看不到这段，它代表"运营这个应用的人"的意志。有的厂商把它作为请求顶层的独立字段，有的把它作为 messages 里的第一条，语义是一样的：**优先级最高的背景指令**。

**user（用户）**：终端用户的输入。也包括你替用户塞进去的东西——检索到的文档、工具的执行结果，都是以 user 侧的身份进入对话的。

**assistant（助手）**：模型的输出。多轮对话里，模型上一轮说了什么，要以 assistant 角色原样放回历史。

要理解一点：**角色只是标记，不是权限**。模型看到的是整段拼起来的对话，它被训练成"更重视 system 的指令、把 user 当对话方"，但这是训练出来的倾向，不是硬隔离。这就是为什么后面会有 Prompt 注入的问题（第 30 篇）——user 内容里一句"忽略上面的指令"，模型并不天然免疫。

---

## content 不只是字符串

上面示例里 `content` 是一个字符串，那是简写。完整形态是**一个内容块（content block）数组**：

```json
{
  "role": "user",
  "content": [
    { "type": "image", "source": "..." },
    { "type": "text", "text": "这张图里的表格，帮我转成 JSON" }
  ]
}
```

块的类型决定了多模态怎么进来：文本块、图片块、文档块（PDF）、音频块……第 01 篇说"现在的模型原生多模态"，落到 API 上就是这个——图片不是转成文字描述再喂进去，是作为一个独立的块和文本并列。

响应侧也是块数组。模型可能返回一个文本块，也可能返回"我要调用某工具"的块（tool_use），也可能先返回思考块再返回文本块。**处理响应的正确姿势是遍历块、按类型分发**，不是直接取"那个字符串"。

---

## 多轮对话：API 没有记忆

这是新手最常踩的坑：**API 是无状态的**。你第二次请求时，模型完全不知道第一次发生了什么。

所谓"多轮对话"，是**客户端自己把全部历史带上**：第一轮发 1 条消息，第二轮发 3 条（上一轮的 user + assistant + 这一轮的 user），第十轮发 19 条。每一次请求，都是从零开始把整段对话重新读一遍。

这带来两个直接后果：

- **历史是你的责任**：存在哪、存多久、怎么截断，全是应用层要做的事。模型不管。
- **成本随轮次线性增长**：第十轮的请求要为前九轮的全部内容付输入费。一场 50 轮的长对话，累计输入 token 是一场 5 轮对话的几十倍。第 10 篇的账单、第 25 篇的记忆管理，根子都在这里。

有一个趋势要注意：部分厂商开始提供**服务端会话状态**——用上一次响应的 ID 续接对话、或者托管的 Agent 会话。这本质上是把"存历史"的活从你的服务器挪到了厂商的服务器，**不是模型有了记忆**，计费依然按每次实际读入的内容算。理解了这一点，就不会被"有状态 API"的说法迷惑。

---

## 响应长什么样

```json
{
  "content": [
    { "type": "text", "text": "模型的回答……" }
  ],
  "stop_reason": "end_turn",
  "usage": {
    "input_tokens": 1200,
    "output_tokens": 350,
    "cache_read_input_tokens": 900
  }
}
```

三个必看的字段：

**content**：块数组，前面说过。

**stop_reason（停止原因）**：模型为什么停了。常见值：正常说完（end_turn）、撞到输出上限被掐断（max_tokens）、要调用工具（tool_use）、安全策略拒答（refusal）。**每次都要检查这个字段**——"撞上限被掐断"和"正常说完"在 content 里长得一模一样，只有 stop_reason 能区分，不看就会把半截 JSON 当完整结果处理。

**usage（用量）**：这次请求各类 token 的实际数量，是账单的唯一真相。输入多少、输出多少、缓存命中多少——生产环境应该把它记进日志，不然月底账单对不上时无从查起。

## 推理模型多出来的东西：thinking 块

开了思考模式（第 02 篇）的模型，响应的 content 里会多出一种块：

```json
{
  "content": [
    { "type": "thinking", "thinking": "……（推理过程，可能是摘要或为空）" },
    { "type": "text", "text": "最终回答" }
  ]
}
```

关于它，四件事要清楚：

1. **它先于正文出现**。流式输出时，思考块的内容（或空事件）会先到，正文后到——界面上"正在思考…"的提示就是靠这个做的。
2. **内容未必给你看**。多数厂商默认不返回原始推理，只给摘要，甚至只给一个空块。但 usage 里的输出 token 照样计入——不展示不等于没生成。
3. **多轮对话时要原样带回**。模型上一轮的响应（包括思考块）作为 assistant 消息放回历史时，思考块要原封不动，有的厂商会对它签名校验，改一个字就报错。
4. **不同模型之间不能互带**。A 模型生成的思考块，喂给 B 模型时会被忽略或报错。做模型切换时，历史里的思考块要处理。

---

## 把链路串一遍

用一次多轮问答走完整个流程：

1. 客户端组装请求：system 指令 + 历史消息 + 本轮用户输入，指定模型和输出上限
2. 服务端把整段内容读一遍（这一步就是"输入 token"），生成响应（"输出 token"，开了思考的话包括思考部分）
3. 响应回来：遍历 content 块，检查 stop_reason，记录 usage
4. 把本轮的 user 消息和模型的 assistant 响应追加到历史，等下一轮
5. 下一轮从第 1 步重来，历史更长了一截

整个系列剩下的内容，都是在这条链路的某个环节上做文章：第 10 篇讲第 2 步的钱怎么算，第 11 篇讲历史太长了怎么办，第 22 篇讲第 3 步返回 tool_use 块时该干什么。
