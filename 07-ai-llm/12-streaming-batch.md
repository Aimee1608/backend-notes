# 流式、异步、批量：三种调用模式怎么选

同一个模型、同一个请求体，可以用三种完全不同的方式提交：**流式**（边生成边返回）、**异步**（提交后去干别的、稍后取结果）、**批量**（攒一堆离线跑，半价）。

它们的差别不在模型能力，在**你的场景对时间的要求**：用户在屏幕前等着吗？任务要跑几分钟还是几秒？结果是现在要还是明天要？这篇把三种模式各自解决什么问题、怎么选说清楚。

---

## 同步调用的两个问题

最朴素的用法：发请求，等模型生成完，一次性收到完整响应。它的问题在生成变长之后暴露：

**等待体验差**。模型生成几百 token 要几秒到十几秒，开了思考模式可能几十秒。同步模式下这段时间用户面对的是空白——什么都没有，直到全部内容一次出现。

**连接撑不住**。推理模式加上多步工具调用，一次请求跑几分钟是常态。HTTP 连接、网关超时、负载均衡器的空闲断开，每一层都可能在结果出来前掐掉连接。大输出量的请求，厂商 SDK 甚至会直接拒绝非流式调用。

三种模式就是对这两个问题的三种回答。

---

## 流式（Streaming）：用户在等，让他先看到点什么

流式的机制是 **SSE（Server-Sent Events）**：服务端不等生成完，每产出一小段 token 就推一个事件过来，客户端逐段渲染。模型"打字机"效果就是这个。

它解决的是**体感**：总耗时没变，但**首字延迟（TTFT）**从"等全部"变成"等第一个 token"，用户几百毫秒内就看到内容开始出现，等待的焦虑感大幅下降。同时长连接持续有数据流动，不会被当成空闲连接掐掉。

流式的事件不只有文字增量。一个完整的流会依次告诉你：消息开始、某个内容块开始（可能是思考块、可能是文本块、可能是工具调用块）、块内的增量、块结束、消息结束并附上 stop_reason 和 usage。**工程上要按事件类型处理**，而不是把所有增量拼成一个字符串——思考块的增量和正文的增量得分开渲染，工具调用块的增量要攒成完整 JSON 再解析。

两个常见的坑：

- **自己的后端也要透传流**。模型到你的服务是流式的，你的服务到前端如果是等全部收完再返回，流式就白做了。整条链路都得是流式的。
- **usage 在最后一个事件里**。要记账单，得等流结束，中途断了这次的用量就拿不到——生产上要有兜底（按已收到的内容估算或标记为未知）。

适用场景：所有**有人在屏幕前等**的场景——对话、写作助手、代码补全。

---

## 异步（Async / Background）：任务要跑很久，别让连接挂着

有些任务本来就不是"一问一答"的节奏：一个跑几十步的研究型 Agent、一份要读几十万 token 的文档分析、开了最高档思考的复杂规划。跑几分钟到几十分钟，流式也不合适——不是每秒都有内容产出，且一旦断连从头再来。

异步模式的做法：**提交请求立即拿到一个任务 ID，连接断开；之后凭 ID 轮询状态或等回调，任务完成再取结果**。厂商侧把任务放进队列执行，你的服务不需要维持任何长连接。

它对应的是经典的"作业系统"模型，工程上要处理的也是那一套：任务状态机（排队 / 执行中 / 完成 / 失败）、轮询间隔、结果保留时长（厂商通常只保留一段时间，过期就取不到）、失败重试。有的厂商还支持"异步提交 + 后续接上流"——任务在后台跑，你随时可以连上去看进度，断了再连。

适用场景：**用户不在实时等结果，但希望尽快拿到**——提交后可以关掉页面、稍后收到通知的那类任务。

---

## 批量（Batch）：不急，要便宜

三家主流厂商都提供 Batch API，规则高度一致：**把一堆请求打包提交，承诺在一个时间窗口（通常 24 小时）内跑完，价格是同步调用的一半**。

半价的逻辑：厂商可以把这些请求安排在算力空闲的时候跑，用调度自由换折扣。所以它不承诺时效——可能几分钟跑完，也可能接近窗口上限才完成。

用法上的几个要点：

- **结果不按提交顺序返回**。每个请求要带自己的标识（custom_id），取结果时按标识对应，不能按位置
- **单个请求可以失败**，其他照常。要检查每条结果的状态，不能默认全成功
- **可以和缓存叠加**。批量里的请求前缀相同（同一个 system + 同一份文档），缓存折扣照样生效，两个折扣乘起来
- **不适合有依赖的任务**。批量里的请求相互独立，A 的结果作为 B 的输入这种链路做不了

适用场景：**离线、独立、量大**——给十万条评论打标签、跑一轮评测集、给整个数据库的商品生成描述、夜间批处理任务。

---

## 怎么选

三个问题依次问：

**用户在屏幕前等吗？** 在 → **流式**。这是唯一能改善"等待体感"的模式。

**不在等，但任务要跑很久、结果要尽快？** → **异步**。用任务 ID 替代长连接，完成后通知。

**不急、量大、想省钱？** → **批量**。半价，24 小时内给。

一个应用里通常三种都有：对话接口走流式，用户触发的"生成完整报告"走异步，每晚的数据清洗走批量。**按接口的时间要求分别选**，不要全用一种。

---

## 一个反向提醒

三种模式改变的是**提交和接收的方式**，不改变模型做的事、不改变 token 计费的基数（批量是打折，不是少算）。所以第 10 篇的成本拆解、第 11 篇的上下文管理，在三种模式下同样成立。选对模式解决的是"等多久"和"花多少"的问题，不解决"答得好不好"。
